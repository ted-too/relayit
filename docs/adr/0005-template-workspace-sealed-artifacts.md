# Template catalog + kinded workspaces with sealed render artifacts

Templates are the send catalog (id **or** auto-generated slug from name; non-unique display name; per-channel variants). Code-backed engines such as React Email are **not** Templates themselves: **Workspace Entries** are pickable assets a Template’s email variant **links by stable id**. Primitive email variants store Resend-shaped `content` `{ subject, html?, text? }` + `variables` map (string/number, optional fallback; no logic) live-on-save on the variant — no workspace. `reactEmail` variants keep only `workspaceEntryId` (`content`/`variables` null).

A Project may have many kinded **Email Workspaces** (`reactEmail` today). Each has a **Workspace Source**; v1 is **`hosted`** only (`github` is a reserved seam). Source of truth is **Git-in-object-storage** (content-addressed objects in S3; **branch refs in Postgres**; per-workspace lock; ephemeral worktrees for install/build — not a Railway volume). Hosted flow: `dev` draft / `main` only after successful Publish. Authors use a Monaco web IDE; platform scaffolds the tree, regenerates the lockfile (public npm only), and runs **deps sync** separately from Publish. Publish materializes Git, hardened-installs in a **templating-builder** service, seals per-entry render artifacts to object storage, and advances `main` only on success. The dashboard talks only to the **API**; the API is a BFF to the builder over the private network for all Git reads/writes, deps sync, and Publish (builder is the sole Git mutator). Message create and Preview run only those artifacts in a constrained render isolate (Preview may ephemeral-seal `dev` without going live). We rejected Handlebars-style IR at save (breaks real templates with arrays/conditionals) and rejected running free-form source on every send. Workspace kinds stay a static registry under `/templating/` so future engines reuse the same build/seal/render path without a second catalog.
