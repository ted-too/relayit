# Overview

How Relayit is put together, and why. [AGENTS.md](../../AGENTS.md) has the glossary and the rules; this page has the decisions behind the shape of the code.

## Shape

```
customer's code ── x-api-key ──► apps/api (HttpApi) ── POST /messages/email, /send/*
                                   │  accept: Message + Delivery + job, one transaction
                                   ▼
                             Postgres outbox ──(relayed by the worker)──► Redis Streams
                                                                              │
                                   apps/worker (no HTTP): every job handler ◄─┘
                                        ├─► SES (packages/provider-aws) ─► recipient
                                        └─► customer's Webhook Endpoints
SES ── SNS ──► apps/api /webhooks/providers/aws/ses ─► bounces, complaints, Suppression

browser ──► apps/web (APP_URL): static build + /config.js (API_URL, read at start)
   │
   └── fetch, credentials, CORS ──► apps/api (API_URL)
                                     ├── /auth/*: better-auth
                                     ├── /config, /projects/…: DashboardApi ─► Postgres, Redis, SES
                                     │      └── Effect Rpc + shared secret ──► apps/template-builder ─► S3
                                     └── /unsubscribe/…: one-click POST (also from mailbox providers)

apps/site: marketing site and public docs
```

The api, worker and builder share one Postgres and one Redis. The domain lives in `packages/*`, which the apps import through explicit subpaths; an app never imports another app's source.

## Decisions

### Four deployables, one database

Template building installs npm packages and runs builds, so it has its own process and lifecycle (`apps/template-builder`) that only the api calls. Public ingress (`apps/api`) and background work (`apps/worker`) are separate deployables too. They began as one process, and that was a mistake: request capacity and worker capacity scaled together and shared a failure domain, so a crash, or a burst of delivery work, hit the API too. Now each scales and fails alone; the price is a service to deploy, and a deployment without the worker accepts sends that queue and never go out. The dashboard (`apps/web`) is the fourth: static files, with no database or credentials.

The api runs one process per replica and scales with replicas, not by forking: its `node:cluster` mode existed to keep the worker on one primary, never ran in production (it needed `NODE_ENV=production`, which the images don't set), and went with the worker. Several workers are safe: they share one Redis consumer group, and a dead one's claims are reclaimed after a minute.

The api, worker and builder share one database and one migration history, in `packages/persistence/drizzle/`, aggregated from the persistence schema and the jobs package's tables. No app applies them. A release runs one migrate step before its apps start (`apps/api/src/migrate.ts`, `bun run migrate.js` in the api image), under a Postgres advisory lock so two steps at once are safe: the second waits, then finds nothing to do. The step retries only its connection, for two minutes, on the schedule the apps' check uses; a migration that fails is never run twice by one step. A generated migration carries no data change, and a hand-written one is not allowed, so the one data fix a migration has needed is in the step itself, in code, run before the migrations: it normalizes stored Contact emails, merging the Contacts that then collide, while the constraint that keeps them normalized is not yet there, and commits that apart from the migrations (`packages/persistence/src/db/migrate.ts`). Each app, before it serves or takes a job, checks that the database has every migration its own image carries (`requireMigrated`). If the database is behind, it waits five minutes for the step and then exits, because a platform may start it while the step is still running, and failing one query at a time is worse than not starting. A database it cannot reach or query gets the same wait and the same two-second retry, whatever the error, since Postgres may be starting too and an exit spends one of the restarts a platform allows; only the last attempt's error fails the app. If the database is ahead, it starts: during a rollout the previous version keeps running against the schema the new release has just migrated. That makes one rule binding on every migration: it must leave the previous release working (add before you use, stop using before you drop, across two releases).

### The dashboard is a client of the api

Everything a signed-in user does runs in the api, and the dashboard only calls it. The api is one host (`API_URL`, api.relayit.io) whose paths start at the root, and the dashboard is another (`APP_URL`, app.relayit.io). better-auth is mounted at `/auth/*` (sign-in, sessions, organizations and members, the GitHub callback `/auth/callback/github`, Stripe's webhook `/auth/stripe/webhook`); the rest (creating a Project, API keys, Domains, Templates, Email Workspaces) is `DashboardApi`, an `HttpApi` contract in `packages/contracts` that the api serves at the root beside the public API (`GET /config`, `POST /projects`, and each Project's resources under `/projects/:orgSlug/…`) and the dashboard calls with the client derived from it. It is a separate `HttpApi` from the public one, so none of it reaches `/docs`: it is the dashboard's, with no stability promise, and the contract package depends on `effect` alone, so nothing server-side follows it into the browser.

One namespace, two kinds of route, told apart by the contract a route is in rather than by its path. An endpoint of `Api` takes an API key in `x-api-key` and sends no CORS headers; a session cookie there is ignored, so a request without a key is refused as the contract tests pin (422 naming the missing header, 403 for an unknown key). An endpoint of `DashboardApi` takes the session cookie and nothing else: an API key there is refused with 401 even beside a cookie, and its routes, with better-auth's and unsubscribe's, are given the CORS middleware where they are built, so a new endpoint can't be served without it (`apps/api/src/auth-rule.test.ts` checks every endpoint of both contracts). If the public API ever serves Projects to API keys, it is the same resource with a second auth scheme, not a second path.

`HttpApi` rather than Effect Rpc because these are plain requests and responses authenticated by the session cookie: each operation gets a readable URL and status, the session middleware is the same shape as the API key one, and errors are typed per endpoint. Rpc stays where it is: between the api and the builder, one service calling another with a shared secret.

Authorisation is in two middlewares, never in a handler. `DashboardSession` resolves the cookie to a user (401 without one). `ProjectAccess` also resolves `:orgSlug` to the user's membership of that Project and checks the role's permission named by the endpoint's `RequiresPermission` annotation against the roles in `packages/persistence/src/auth/permissions.ts`; an unknown Project, a non-member and a missing permission are all 403, so a Project's existence isn't revealed. A handler sees only `DashboardMember`, and every query it makes is scoped to that Project's id, so an id taken from another Project finds nothing (404). A change must name the dashboard's origin (`APP_URL`) in `Origin`, as better-auth requires on its own routes: these handlers call `auth.api` directly, which skips better-auth's check, so the middleware makes it. The session cookie is `SameSite=Lax`, which already keeps it off another site's POST.

The dashboard is a Vite + TanStack Router single-page app on its own origin, calling the api cross-origin. It was a TanStack Start app with server-side rendering; behind sign-in, rendering on the server bought nothing and needed a server of its own with every credential. It stays a separate deployable rather than files the api serves: the api is the API's host and nothing else, and the dashboard can be deployed, cached and rolled back on its own.

Cross-origin, done once: the api grants CORS to `APP_URL` exactly, with credentials, on better-auth's routes, every `DashboardApi` route and unsubscribe, answers their preflights, and grants no other origin. The public API sends no CORS headers (it is called by servers holding a key, never from a page), so its preflight stays the 404 the contract tests pin. better-auth's base URL is `API_URL` and it trusts `APP_URL`, so sign-in, its CSRF check and every redirect after sign-in (GitHub's included, which returns to the api and is sent on to the dashboard) accept that origin alone. A failure better-auth can't send back to the page that started the sign-in (an OAuth callback whose state is gone) goes to the dashboard's sign-in page, not better-auth's error page on the api. The session cookie is the api's, `HttpOnly` and `SameSite=Lax`: Lax is sent on the dashboard's fetches because `app.` and `api.` of one domain are the same site, as are two ports of localhost in development. Two hostnames that are not one site (two unrelated domains, or two subdomains of a public suffix such as `up.railway.app`) are not supported: the cookie would need `SameSite=None`, which browsers increasingly block as a third-party cookie. `AUTH_COOKIE_DOMAIN` widens the cookie to the parent domain only so the marketing site can see a visitor is signed in; the dashboard doesn't need it.

No deployment's URL is in the build, because self-hosters run the published image. The image is nginx and the build, with no JavaScript runtime (`apps/web/nginx`): its entrypoint checks `API_URL` as the container starts and writes its origin into `/config.js`, which `index.html` loads before the app. The rest is the build, compressed once at image build: a file that exists as it is (`assets/` cached for good, everything else revalidated), and `index.html` for any other path (a path may have a dot in it, `/acme/domains/mail.example.com`, so the extension decides nothing). A missing file under `assets/` is a 404, so a stale tab fails loudly instead of parsing the page as a script. In development Vite answers `/config.js` the same way, and the dashboard on `WEB_PORT` calls the api on `API_PORT` cross-origin, so CORS and cookie mistakes show up there rather than in production.

Unsubscribe links point at the api (`API_URL/unsubscribe/:orgSlug/:contactId?msg&topic&sig`). A mailbox provider's one-click POST is answered there without a cookie; a person who opens the link is redirected to the dashboard's page at the same path on `APP_URL`, which sends the same POST when they confirm. A GET never unsubscribes, because link scanners open every URL in a message.

A Project's slug names it in every URL (the dashboard's `/<slug>`, the api's `/projects/<slug>/…` and `/send/<slug>/…`), so it is held to one rule, `ProjectSlug` in the contract: lowercase letters, digits and single hyphens, 2 to 48 characters. better-auth's organization hooks in `createAuth` check it, so no create or rename escapes it, and a new Project's slug is derived from its name to pass it (`projectSlugFromName`). It is the first segment of the dashboard's URLs, so the dashboard's top-level pages and `assets/` (`RESERVED_PROJECT_SLUGS`) are refused too; its other root files (`config.js`, `favicon.ico`) have a dot, which no slug can. The api's paths don't matter here: it is another host.

### Work crosses processes as typed jobs

A job's contract (`defineJob`: name, payload schema, retry and dead-letter policy, recurrence) belongs to its domain package, next to its handler. The api imports contracts and enqueues; only `apps/worker` imports and registers handlers, so producing a job never decides where it runs. An HTTP handler never does delivery or infrastructure work itself.

A job that depends on rows being written is enqueued through the Postgres outbox in the same transaction, so a send is never accepted without its delivery job, nor a job left pointing at rows that rolled back. The outbox publishes to Redis Streams; a crashed worker's claims are reclaimed after a minute; a job that exhausts its retries is dead-lettered in Postgres. A handler that dies (a defect, not a typed failure) has failed that attempt of its own job and nothing else: it is retried and in the end dead-lettered with its `onDeadLetter`, which is given a `JobHandlerDefect`, so a bug in a handler neither interrupts the rest of its batch nor leaves what the job was for (a Delivery) without an outcome. A defect outside the handler leaves the job pending for the reclaim loop.

### `/messages/email` is Resend-compatible

Transactional email is sent with `POST /messages/email`, shaped like Resend's send-email API so a Resend client can point at Relayit with minimal change. Relayit-only fields may be added, never required. It creates a transactional Message and one email Delivery; it is not a second concept and never sends marketing. Two incompatibilities are deliberate: a body with `topic_id` is refused (`422`), because Topic consent belongs to Campaign sends and a sender who names a Topic would believe it had been applied; and webhook event types are channel-agnostic (`message.sent`, `delivery.skipped`), not Resend's `email.*`. The categories match (delivery outcomes, Domain and Contact lifecycle); the names don't. Every other field the schema does not know is dropped, not refused, so a Resend client sending one keeps working; the OpenAPI generator would declare each object closed, so `Api` reopens the ones `/messages/email` takes. The legacy `/send/*` stays for existing integrations.

The api is an Effect `HttpApi` (`apps/api/src/api.ts`), but its responses are the ones the Elysia server it replaced answered with: the same statuses, bodies, field order and content types (`application/json;charset=utf-8`), a bare `400 Bad Request` for a body that isn't JSON and `404 NOT_FOUND` for an unrouted path. A send's API key is verified before any of its body is read, so a client without a good key can't make the api hold up to 50 MiB per connection: the auth middleware runs first (`beforeBody`), then `RequestValidation` reads and checks the body, after which the endpoint's own decoding never fails. Only a `Content-Length` over the limit (`413`) is answered ahead of the key, and a path or header that fails its schema still answers in place of the key's failure, which is why a missing `x-api-key` on `/messages/email` is a `422` and not a `403`. Elysia validated the whole request before the key; what changed with the order is only the answer to a request with a bad body and either a bad key, which is now about the key, or a valid key whose Project has no owner, which is the `500` that Project already got for a good body. `apps/api/src/contract.test.ts` pins all of it; a change there is a change to a customer contract.

Every route of the api is held to a body limit by one route middleware (`apps/api/src/lib/body-limit.ts`), given to all the routes at once in `http.ts`: 1 MiB unless the route is named in that file's `exceptions`, so a route added later is limited without anyone asking, and one that legitimately receives more answers `413` until it is named there with its own number. A `Content-Length` over the limit is refused before the route runs; a chunked body is not read ahead, so a route still checks who is asking before any of it is read, and the read that passes the limit is answered `413` by the middleware. That covers the buffered reads (a contract's payload, `text`, `json`, `arrayBuffer`), not `request.stream` or multipart: a route that streams an upload caps it itself and is named `"own"`, as the send endpoints and the SES notification route are, because they answer differently (the sends after the key and as the customer contract's `413`, SES as the `400` SNS does not retry). better-auth reads a web `Request` itself, so `routes/auth.ts` reads the body under the limit and hands it over. An answer given with the body unread closes the connection, because Bun stops reading a body nobody consumes and would hold the connection for it until the idle timeout.

### Accept, then deliver

Accepting a send is synchronous and cheap: validate, drop recipients suppressed at severity `all` (the response lists them), reserve Usage, then write the Message, its Delivery, its Contacts and the delivery job in one transaction. An `Idempotency-Key` header makes a retried request within 24 hours return the original Message rather than send twice.

If the accept ends any way but success (a failure, a defect, the client disconnecting, even during COMMIT or with COMMIT's answer lost), Relayit reads back whether the Message was written, and only if it was not are the Usage reservation released and the staged attachments removed. A failed COMMIT is not proof of a rollback: the server may still be finishing it, or may only receive it after the client's connection has gone. So the accept's transaction holds a transaction-level advisory lock keyed by the Message id, which Postgres releases only once the commit is visible or rolled back, and the read-back takes that lock before it reads. It tries three times, waiting a second for the lock each time, so a failing accept is held about three seconds at most. If the lock is not had or the read fails, both are kept: a reservation may leak, but a committed send never loses its attachments. A leaked reservation holds its place in the counts until its billing period ends, and expires 90 days after that, as does any reservation never confirmed or released; a release that finds its reservation gone has nothing to give back and is not an error. A delay before a second read was rejected because no delay bounds a commit.

An attachment is recorded as staged before its upload starts, so one interrupted mid-flight is deleted whether or not it landed. An upload that reaches storage after that delete ran is the one object that can be left behind.

The worker strips suppressed recipients again before sending, since a bounce may have landed in between: severity `all` for every send, `marketing` as well for a marketing one, by the Message's own purpose and not the job's. A Delivery whose recipients are all suppressed ends `skipped`; one that cannot be sent ends `failed` with its reason. Each outcome emits its webhook event in the transaction that records it.

**The claim.** Jobs run at least once, and a reclaim can run one job twice at the same time, while SES takes no idempotency key; so the Delivery's status is what keeps a send from going out twice. A run sends only after claiming the Delivery from `queued` to `sending`, which stamps `startedAt`.

The claim's `WHERE` also requires that the sender may send: the Domain is not paused and the Project still holds it, or the Sandbox Domain is active and not paused. Checked before the claim, with suppression lookups and attachment loading in between, a pause or another Project's proven claim could land in the gap and the old holder got one more send out. A claim that matches nothing reads the same conditions back to tell a sender that may not send from a claim another run made. A change that lands after the claim, while SES is being called, still lets that send out.

The claim's `WHERE` requires, too, that none of the recipients the run kept is suppressed, with the condition the strip uses, for the same reason: attachments load between the strip and the claim, and a bounce or complaint landing there got one send to a suppressed Contact. A claim refused while the Delivery is still `queued` and its sender may send is not a failure and not another run's claim: a kept recipient was suppressed, or what refused the claim (a Suppression, a pause) was lifted before the run read why. The run strips again and claims again, within the same attempt, so the remaining recipients are not made to wait for a retry or failed on a last attempt, a Delivery with none left ends `skipped` as it would have at the strip, and one refused for something since lifted is not left `queued` with no run to take it. A run makes at most five such passes, since a Suppression or pause set and lifted over and over could otherwise hold it for ever, then leaves the Delivery to the job's retry, or on the last attempt to the dead-letter step, which fails it. The claim writes the recipients it sends to onto the Delivery, so the row names who the send went to and a bounce is matched against them; no Webhook Event names a recipient stripped by the worker (#85). A Suppression that commits after the claim, while SES is being called, cannot stop that send: SES has no recall, and holding a lock on the Contacts across the SES call would make every bounce and complaint for them wait on a network request of up to 30 seconds. Unsubscribes are not part of the strip or the claim, because no marketing send is accepted yet; the Campaign send has to add them to that one condition (#86).

**One attempt, on its own connection.** The SDK never retries SendEmail (`maxAttempts: 1`): a send it retried after a reset or a 5xx could reach the recipient twice, so only the delivery job decides what follows a send.

Each SendEmail opens its own connection (`keepAlive: false`), at the cost of a handshake per send. A kept-alive connection that SES or the network dropped while idle fails the next write with the same reset as a send SES took and never answered (under Bun the SDK reports both as a `TimeoutError`, "read ECONNRESET"), so it had to count as an unknown outcome and the Delivery ended `failed` though nothing was sent. On a new connection a send that cannot reach SES fails at connect, which is proof. Retrying a write "that never left" was rejected because nothing tells it from one that did: Bun names the syscall `connect` only when no connection was made, which `ses.test.ts` pins.

**SES's answer.** It goes to Redis (keyed by the Delivery and the claim) the moment it arrives, then to Postgres; the claim, the send (bounded by a 30-second timeout) and those writes run uninterruptibly, so a worker shutting down finishes them. A run that finds the Delivery `sending` never sends it: with an accepted answer in Redis it records `sent`; with a refusal it requeues it, unless the refusal was of the message itself or for a Project Sending Pause; with no answer it retries while the claim is within its two-minute lease, since its owner may still be sending, and fails it once the lease has run out. A run that only lost the claim to another never fails the Delivery; the winner has retries of its own. The kept refusal says which kind it was, and a Project Sending Pause's region, because whoever ends the Delivery may not be the run SES answered: that run's write can fail, and then a later run, the dead-letter step or `endStuckDeliveries` ends it. Each fails it with the reason the first run would have given, and for a Project Sending Pause pauses the Project's Domains in the same transaction, without asking SES again.

**Refusals.** Only an error that proves SES never took the send puts the Delivery back to `queued`: a rejection, a throttle, a validation, authentication or configuration error or any other 4xx SES answered with, or a DNS, connect or TLS failure before the request went out. A timeout, a connection dropped after it was made, a 5xx or an unreadable answer leaves it `sending`, since SES may have taken it.

Most refusals are retried, because they can pass within the job's retries (five attempts over about eight minutes) without anyone acting. `MessageRejected`, and an attachment that cannot be encoded, fail the Delivery on that attempt instead. `MessageRejected` is not only bad content: SES also answers with it when it does not count the sender, or for an account still in the SES sandbox a recipient, as verified in the region. Those are states of the Domain or the account, not of the message, but someone has to fix them first, which the retries do not outlast; failing at once tells the Project now rather than eight minutes later.

An authentication failure is deliberately still retried. It is the deployment's condition (credentials being rotated, an IAM change still propagating) and can clear by itself within the retries; failing at once would fail every queued send during a rotation.

**Outcomes that cannot be written yet.** An outcome that can't be written (Postgres down) fails the job's dead-letter step, which leaves the job pending, and the reclaim loop runs it again until the outcome is written. Usage confirmation after SES has accepted is bookkeeping: its failures retry or are logged, never fail the Delivery.

**A Delivery whose job is gone.** Everything above is done by the Delivery's job, so a Delivery whose job no longer exists (lost with Redis's data after the outbox published it, or from before a dying run ended its Delivery) would stay `queued` or `sending` for good. The worker therefore ends, as it starts and every hour, each Delivery that has been `sending` for more than a day (`endStuckDeliveries`), as the job's dead-letter step would have: `sent` from an acceptance still kept in Redis, otherwise `failed` with `message.failed` and its Usage released. A Delivery still `queued` a day after it was accepted, and a day after its `scheduled_at` if it has one, is failed the same way, unsent. It never looks for the job. Nothing bounds how long a job can be held up (a backlog, no worker running, a dead-letter step that cannot write), so the day is a margin and not a limit. What makes it safe is that the reconcile and a late job write the same outcome under the same guard, so whichever comes second, or a second worker reconciling at that moment, finds it written. The one thing a late job would have done differently is send again after a refusal whose requeue was never written, which is why the margin is a day and not an hour. It must stay well under the seven days the answer is kept in Redis, or a send SES accepted would be failed.

A `queued` Delivery is failed and never given a new job, though SES was never called for it (the reasons are on `STUCK_AGE`). The claim's `WHERE` holds a send to the same day, so a Delivery whose job is only late is not sent either: the run's claim is refused and its dead-letter step fails it with the same reason, unless the run ended it for something it checks before the claim (every recipient suppressed, a Domain no longer verified). What that costs spans the deployment: a worker that was down for more than a day fails, as it starts, what was accepted before that day instead of sending it.

What that guarantees: an accepted Message is sent at most once, except while workers from before this design and after it run side by side (the old handler re-sends a `sending` Delivery). A client that loses the response to an accept, even mid-COMMIT, may find the send accepted; retrying it without an `Idempotency-Key` makes a second Message. A Delivery can end `failed` though SES delivered it when SES took the send but its answer never reached Relayit (the timeout, a dropped connection or a 5xx after acceptance), when the worker died between SES's answer and the Redis write, or when that answer could be written to neither Redis nor Postgres before the claim's lease ran out.

### SES tenant per Project

All Projects on the platform's SES account share that account's bounce and complaint rates, so one Project mailing a stale list could get the account paused and stop everyone's mail. Sends therefore go through an SES tenant per Project (`relayit-<projectId>`, derived, not stored), with SES's Standard reputation policy pausing only that tenant. The worker ensures the tenant on a Project's first send from a region in each process: it creates the tenant there and associates the Domain identity and the shared configuration set. A Domain identity is detached from its tenants before it is deleted, since SES refuses to delete an associated one.

Ensuring the tenant fails open: if it fails (IAM lacking `ses:*Tenant*`, say), the send goes out untenanted and the next send tries again. A `SendingPausedException` is a Project Sending Pause only when `GetTenant` reports the tenant `DISABLED`. Otherwise it is paused for no one in particular: the whole account, or a tenant whose status could not be read. Credentials without `ses:GetTenant` get one warning of this per region and process, and reach it only in the process that created the tenant, for the Domain it was created with: everywhere else the ensure itself needs `GetTenant`, fails with its own warning on each send, and the send goes out untenanted, which a tenant's pause does not stop. That send is retried, since an account's pause may end, and fails as "SES paused sending" with no Domain paused: pausing on a guess would leave a Project's Domains paused after an account's pause, with a recheck that cannot read the status either.

SES pauses and restores a tenant by itself, in one region at a time, so Relayit follows the tenant's status instead of waiting for a send to hit it. A Project Sending Pause pauses every Domain the Project holds in that region, with the reason `project_sending_pause`, and each emits `domain.updated`; SES restoring the tenant unpauses them. Relayit hears of a change two ways: a send SES refuses for it, and SES's `Sending Status Enabled` and `Sending Status Disabled` events, which a rule on the region's default event bus forwards to the notification topic and so to the api. Both go through the same pause (`pauseProjectDomains`), which leaves an already paused Domain as it is, so the Project is told once whichever arrives first and however often.

An event is only a reason to ask. SES delivers them late, twice and out of order (seen in the deployment's account: three changes made by hand within two minutes arrived out of order), each reports one of a tenant's two statuses, its owner's or SES's own, and `Sending Status Enabled` covers `REINSTATED` as well as `ENABLED`; a tenant cannot send while either status is `DISABLED`. So the api reads nothing of the status in an event. It asks SES for the tenant's `SendingStatusAggregate` (`GetReputationEntity`), the two combined, and acts on that: `DISABLED` pauses, `ENABLED` and `REINSTATED` unpause, and an answer it does not know or cannot get is a 500, so SNS brings the event back. A Project with no tenant in the region is unpaused like an enabled one: SES has paused nothing of the Project's there. The read and the write after it hold an advisory lock per Project and region, so of two syncs running at once the one that read the older status cannot write last. A sync waits three seconds for that lock and then fails, to be tried again, so one stuck on SES does not queue the rest behind it, each holding a connection.

Events alone cannot be what lifts a pause. One can be lost: SNS drops it after an hour of 500s, or an api that lacks the permission to ask SES fails every retry. And the delivery handler pauses from the refusal it got, without the lock or a second look, so if SES restores the tenant just after refusing a send, the api can handle the "enabled" event, find nothing to unpause, and the handler's pause lands afterwards with nothing left to lift it. So every pause Relayit makes schedules a recurring job for that Project and region (`email.recheck-project-sending-pause`), which runs the same locked sync every five minutes for as long as a Domain there is paused as `project_sending_pause`, and ends once none is: a run that finds nothing paused asks SES nothing and schedules no other. Nothing cancels a scheduled run, because a pause that is committing at that moment has just scheduled it and cannot be seen yet. A run that fails at any step schedules the next as it fails, so a database, Redis or SES that is down for one run does not end the checks, and a starting worker schedules one for every such pause, three seconds apart, whatever became of the schedule.

A run SES refuses for the credentials or the configuration (no `ses:GetTenant` or `ses:GetReputationEntity`, or a Domain registered in a region no longer in `SES_REGIONS`) is not a failure: no retry gets past it, and failing would dead-letter a job every five minutes for each paused Project until an operator acted. It logs a warning naming the permissions, and the next run is an hour on and marked as following a refusal, so it and those after it are refused quietly; the first one SES answers goes back to five minutes. The mark is in the scheduled job's payload, so nothing is stored for it, and a schedule written by anything else (a new pause, a starting worker) is unmarked and warns once more. An hour is therefore how long a pause can outlast the operator's fix, unless a worker restarts.

Five minutes is how long a Domain can refuse sends after SES restored the Project when no event said so. Each run is two SES calls, and SES allows one call a second in a region for every action but sending, which cannot be raised. One paused Project and region therefore costs 1/150 of that: a tenth of it at 15 paused at once, all of it at 150, which is why the starting worker's are three seconds apart and not one. Five minutes was kept because a deployment has few Projects paused at once and each minute is a customer's mail refused; a run SES throttles fails, is retried with backoff and is followed by the next in any case. A deployment with dozens paused at once should lengthen it. A sweep of every paused Project on a timer was rejected: it needs a cap and a fair order to bound its SES calls, where a job per pause is bounded by what it is for.

The automatic pause has its own reason because it is the only pause Relayit may lift. An admin can pause a Domain for reputation too (`bad_reputation`), and that pause must outlast SES restoring the tenant, so the unpause matches `project_sending_pause` alone. An admin who wants one of Relayit's pauses to stay pauses the Domain again with a reason of their own ("Keep paused" in the admin's list): the reason changes without an unpause. If Relayit lifts the pause in the moment before the admin's write, that write pauses the Domain again, and sends could pass in between. An admin's pause and unpause emit `domain.updated` like Relayit's, in the transaction that changes the row and only when it changes, or a receiver that saw a pause would never hear of an admin lifting it. A reason rather than a column recording who paused: the reason is already what members, admins and `domain.updated` show, and who lifts the pause is the one thing the two differ in. Domains the worker paused as `bad_reputation` before the reason existed cannot be told from an admin's and wait for an admin.

The automatic pause is the pause of the Project that held the Domain when SES paused it, not of the Domain. So a proven claim lifts it in the transaction that moves the Domain, and tells the new holder: the previous holder's recheck no longer sees the Domain, and nothing was scheduled for the new holder. It stays only when another of the new holder's Domains in the region is paused for the same reason, since SES then pauses that Project there too and its own recheck lifts both. SES is not asked during the transfer, which holds the Domain's row; a new holder SES pauses that Relayit has not yet seen paused (it has only sent from the Sandbox Domain, #95) gets the Domain unpaused, and the first send SES refuses pauses it.

A tenant in an event is trusted no further than the topic it arrived on. The rule matches tenants named `relayit-…` in its own account and region; the api checks the event's account and region against the topic's, maps the tenant to a Project by the same naming rule that names tenants (`sesTenantNameFor`), and looks the Project up before it asks SES anything, so a tenant that is no Project's (the account can hold others) costs no SES call and changes nothing. A Project with only the Sandbox Domain has no Domain to pause, so its pause still shows only as failed sends (#95), and SES's advisor findings, which come before a pause, are not read (#96).

Per-Project configuration sets were rejected because they give metrics but no enforcement; a Relayit-side bounce-rate breaker because it rebuilds what SES's reputation policies already do, without changing how SES attributes reputation.

### Setup assistance, not a provider proxy

Relayit helps a Project finish the setup a vendor needs before it can send, and stops there; it does not proxy the vendor's control plane, which was too much work for what customers need. For email that means Relayit generates the Domain's DKIM key (BYODKIM), registers it with SES, and lists the DNS records the customer publishes, then polls until they verify. The Sandbox Domain's records are on Relayit's own Cloudflare zone, so Relayit publishes them itself. SES names an identity by its FQDN alone, with one DKIM key, so a Sandbox Domain's root and every name under it are refused as a custom Domain: one added there would take over the identity all sandbox mail is signed with, and removing it would delete that identity. The reverse is refused as the worker starts: no Sandbox Domain is created or registered on a root a Project holds as a custom Domain, or holds a name under, and the start logs which Domain is in the way. A Sandbox Domain already registered is not stopped by one found later, since by then the identity is its own. Each refusal reads the other side's rows and then writes its own, so the two are ordered by one advisory lock (`lockSandboxRoots`): setting up a Sandbox Domain holds it exclusively while it checks for a Domain and writes its row, and a new custom Domain holds it shared while it checks again and writes its own, so adds never wait on each other. It is one lock for every root, not one per name, because the refusal covers the names under a root. A root is one name in any case: it is found and kept unique by its lower case, and a new one is stored that way, so `CF_ROOT_DOMAIN` typed in another case is the same Sandbox Domain.

The SES account can hold identities Relayit did not make, by hand or from another system on the same account, and a Project that adds such a name has proven nothing about it. So Relayit takes an existing identity as a Domain's only when it signs with that Domain's own DKIM selector, which is generated at random for one Domain and which SES reports back for a BYODKIM identity: that is the identity an earlier attempt at the same registration made. Any other is refused (`EmailBackendIdentityConflict`), neither re-keyed nor replaced, and a Domain that is removed deletes only the identity signing with its selector, so a refused Domain can't delete the identity on its way out. A refusal can't be finished by adding the name again, so it takes back what the refused request wrote: a first add's Domain, and a claim on an unregistered Domain, which would otherwise keep a place in the Plan's Domain limit until it lapsed. A holder whose retry is refused keeps the Domain, which was there before the request, and removes it by hand. A Domain refused on its first add never had an identity, so its removal records none: every later add of the name would ask SES about the record. The selector was chosen over a tag because every identity made before this rule already carries it and reading it needs only `ses:GetEmailIdentity`. The one identity that signs with another selector and is still Relayit's is that of a removed Domain whose delete job has not run; it is recorded in `removed_domain_identity` in the transaction that removes the Domain, and a registration of the FQDN deletes what is recorded there before it creates its own. A record costs every registration of its FQDN an SES call inside the registration's own timeout, so none is kept past its use. The delete job clears it with the identity. When SES had none of the Domain's, a create that was given up on can still land, and the record is what lets an add in that time delete it; the job queues itself to look once more fifteen minutes later (`LATE_IDENTITY_GRACE_MS`), deletes an identity that landed late, and clears the record either way. Giving a call up aborts its request, so only a request SES already had can land, within seconds; fifteen minutes is a margin, not a measurement. A record whose job was dead-lettered stays, because its identity may still be in SES, until an add of the FQDN deletes both. An identity Relayit made that is in neither place, such as one whose delete job was queued by a release before the record existed and then lost, blocks its FQDN until someone deletes it in SES.

### One SES account, configured by ops

A deployment sends through one SES account, named in the environment of the api and the worker (`SES_ACCESS_KEY_ID`, `SES_SECRET_ACCESS_KEY`, `SES_REGIONS`); the database holds no vendor credentials and customers bring none. Code sends and registers through the `EmailBackend` service (`packages/channels/src/email/backend.ts`), implemented for SES and for the fake in `packages/provider-aws`. Pluggable providers, Project-owned credentials and Domains paired with several providers were removed: each multiplied the paths a send could take for customers who never asked for them.

The account can span several regions, so a later channel can route by destination without the customer choosing; email uses that only to place Domains. A Domain is registered in one region, the first of `SES_REGIONS` when it is added, recorded on its registration (`email_domain_provider_identity`, a name kept so its rows did not have to move), and always sent through that region: there is no failover between regions. A registration with no recorded region predates regions and is in the default one, so the first entry of `SES_REGIONS` must stay the region those Domains were registered in. A send SES refuses is retried with backoff unless the refusal is a Project Sending Pause or of the message itself (see Accept, then deliver); when the retries run out the Delivery fails with that reason.

A Domain goes with its last link, holder's or claimant's: the transaction that removes the link removes the registration, DNS rows and row with it, holding the Domain's row so a claim arriving at that moment either lands first and keeps the Domain or finds the row gone and adds the FQDN as new. A row can outlive the Project that sent from it in one way only, by another Project's claim: a holder that removes the Domain while a claim is pending leaves the row to the claim, and a proven claim takes the row, registration and DKIM key from the holder. An FQDN added when no Project is linked to it is always a new Domain with a new DKIM key.

What a Project sent from a Domain stays with that Project and with nothing else, so it is detached from the Domain when the Project stops holding it, not when the row goes: when the holder removes it, and for the holder that loses it when a claim is proven. A claim never proven has sent nothing from the Domain, since only the holder sends, so removing or lapsing one detaches nothing. Each Delivery names exactly one of a Domain, a Sandbox Domain or `removed_domain_fqdn`, by a check; detaching moves the Project's Deliveries from the first to the third and clears the Domain from their events. Each update finds its rows in the database through the Message's App Environment, so only that Project's rows move and no list of ids comes back to the application: a Project has more Deliveries than a query takes parameters. Deleting the row moves whatever still names it, and the foreign key refuses the delete otherwise, so a Delivery can lose its Domain only this way and accept can't write one with none. A deleted Project's Messages, Deliveries and events go with it by cascade. The FQDN is kept as text so that nothing joins it: a Domain added later under the same name, or the same row in another Project's hands, must never collect these Deliveries, their events or their counts, so nothing may look a Domain up by `removed_domain_fqdn`. Whatever takes a link holds the Domain's row while it detaches, and whatever writes a Delivery or an event naming a Domain takes that row first and then reads what it depends on again: accept reads the Project's link and refuses the send if it is gone, and SES ingest reads the Delivery's sender, so an outcome reported for a detached Delivery is recorded naming no Domain, still suppressing the address in the sender's App Environment and counting toward no Domain. The delivery handler's Project Sending Pause takes the rows of the Domains it will pause before the Delivery for the same reason: every Domain the Project holds in the region, in id order (`lockProjectDomains`), because SES refuses all of a paused Project's sends at once, each from its own Domain. Pausing and lifting a pause take the rows they write in the same order first, since an update takes its rows in whatever order it finds them. It takes them `NO KEY UPDATE`, which keeps out a removal or a transfer and lets accepts through, and pauses only Domains the sending Project still holds. A Delivery still `queued` when its Project's link goes fails in the handler as one whose Project no longer holds its Domain, and stays failed if that Project adds the FQDN again. Nothing lists or filters Deliveries by Domain today; a query that does must decide what a detached Delivery is to it. Detaching rewrites every Delivery the Project sent from the Domain in one transaction while holding the Domain's row, so it is slow for a long history, and sends from the Domain and claims on it wait meanwhile (#102).

The SES identity is deleted by a job enqueued in the transaction that deletes the row (`email.delete-domain-identity`), whose payload names the FQDN, the region and the Domain's DKIM selector because the row is gone when it runs. SES names an identity by FQDN alone, so that job and a registration of the same FQDN take one advisory lock; the job leaves the identity alone when the FQDN is registered again or the identity signs with another selector, and a registration creates nothing once the Domain's row is gone. The Sandbox Domain's registration takes the same lock for its root, and deletes what `removed_domain_identity` records for it first, as a custom Domain's does: the delete job leaves a Sandbox Domain's name alone, so a root that was a Project's Domain would otherwise be refused for that Domain's leftover identity at every start. The lock orders the two only while each SES call answers. A call is given up after 30 seconds so that one which never answers can't pin a connection and the locks, and giving it up releases them while the request may still reach SES late. In those rare orderings a late delete, the job's or the one a registration makes of a removed Domain's identity, can take the identity of a Domain registered since, leaving a registered Domain without one, and a late create can leave an identity whose Domain has no registration or no row; nothing detects either. A Project's deletion is better-auth's and takes the links by cascade, where no code sees the last one go: the api reads them in `beforeDeleteOrganization` and removes the Domains left without one in `afterDeleteOrganization`, and the worker sweeps every Domain as it starts, removing those without a link.

SES allows one control-plane call a second in a region for the whole account, and every Project's registrations and verification checks share it, while a Plan limits how many Domains are held and not how often one is added. So the dashboard's api counts each Project's adds and refreshes in Redis, in fixed ten-minute windows as better-auth counts `/auth/*`, and answers 429 past ten adds or thirty refreshes, before SES is called (`limitSesCalls` in `apps/api/src/dashboard/domains.ts`, where the arithmetic is). It is in the api's route, not the lifecycle, because only a member's request is repeated at will: the seed and the worker call the lifecycle too. The same count bounds how fast the records above are made, at ten removals a Project in ten minutes, not how many there are: while SES is down each removal's delete job retries for about an hour and its record stays, and a record whose job is dead-lettered stays until an add of the FQDN clears it. A long outage with someone adding and removing one name throughout could leave that name enough records to time out its registration.

A claim's first ownership check is scheduled in Redis after its link commits, so it can fail or be lost, and the link records no next check until one has run. The worker's startup reconcile therefore schedules every unproven link, taking one with no next check as due now, so a claim always reaches the check that proves it or lapses it. A Domain's first verification is scheduled the same way, after its registration commits, so the reconcile treats a registered Domain with no next check the same: due now. One with no registration is left alone, since there is nothing to check until an add registers it. The Sandbox Domain's first check is scheduled the same way and reconciled the same way; a start that finds it unregistered registers it.

At startup the worker creates, in every region, the configuration set each send names and an SNS topic subscribed to the api's SES notification URL. The resources are named after that URL, so a restart with the same URL finds them and changes nothing; that is also why the URL keeps its old `/webhooks/providers/aws/ses` shape.

Beside them it puts the EventBridge rule for tenant status events (see SES tenant per Project), with the topic as its target, and adds one statement to the topic's policy letting `events.amazonaws.com` publish from that rule alone. The policy is read and written back with the statement added, never replaced: the default statement in it is what lets SES publish its notifications, and a policy the worker cannot read is left alone. The same topic and route carry both, rather than a second topic or an SQS queue, so the events pass the checks below and need nothing new to deploy; the api tells an event (`detail-type` and `source`, no `eventType`) from a notification after those checks. Like the tenant, this fails open: without `events:PutRule`, `events:PutTargets` or `sns:GetTopicAttributes` the worker logs a warning and starts. No event then arrives, so a Project Sending Pause is noticed only by a send SES refuses, and a restore only by the recheck job, within its five minutes. The recheck and the api's handling of an event both need `ses:GetTenant` and `ses:GetReputationEntity`; without those nothing is lifted, every event is answered 500, and the recheck warns and asks again hourly. Nothing removes the rule, as nothing removes the topic or configuration set. A rule that has just been created matches nothing for about its first minute (in the deployment's account, a status changed 20 to 30 seconds after the rule was made produced no event, and one changed after 60 seconds did), so an event in the minute after a worker first makes the rule can be missed. Later starts put the same rule again and lose nothing. A missed restore is lifted by the recheck job; a missed pause is found by the next send SES refuses, as before the rule existed.

SNS signs every topic's messages alike, so a valid signature proves only that the message came through SNS, not from this deployment: anyone can subscribe the api to a topic in their own account and publish a bounce. The api therefore reads a message, or confirms a subscription, only from the topics the worker makes: it derives their names from its own `API_URL` and their account from STS with the `SES_*` credentials. The api and worker must share `API_URL`, `SES_*` and `SES_REGIONS`, or the api rejects every notification. Removing a region from `SES_REGIONS` stops the api trusting that region's topic, so late bounces and complaints for mail already sent through it are refused; keep a region listed until its mail has aged out. Each notification's SNS `MessageId` becomes its Delivery Event's id, so a redelivery records nothing twice.

A notification is matched to its Delivery by SES's message id, which the worker writes just after SES answers, so a notification can arrive first, or during a Postgres outage after SES accepted. One that finds no Delivery is therefore not acknowledged while the message is young: within an hour of the time SES took it (`mail.timestamp`, inside the signed message) ingest fails and the api answers 500, logged as information, not as an error. Past the hour, or with no readable time, it is acknowledged and dropped: the id belongs to a send whose answer never reached Relayit or to mail this deployment did not send, and nothing may make SNS retry for ever.

A 500 only helps while SNS retries, and its default for an HTTP/S endpoint is three retries twenty seconds apart, after which the notification is discarded. So on every start the worker sets a delivery policy on the topic, built from the same hour (`sesNotificationDeliveryPolicy` from `UNRECORDED_SEND_GRACE_SECONDS`): six retries five seconds apart for the usual race, then one a minute for the rest of the hour. An hour is the most SNS allows an HTTP/S policy in all, so an outage longer than that still loses the notifications sent early in it; nothing but a dead-letter queue on the subscription would keep those. The policy is on the topic rather than the subscription because it can be set before the subscription is confirmed and survives its being made again. It needs `sns:SetTopicAttributes`; without it the worker logs a warning, SNS's default stays, and the rest of the infrastructure is still ensured. Holding early notifications in Redis until the Delivery is recorded was rejected: within the hour SNS keeps and redelivers them itself.

### DKIM keys are sealed

DKIM private keys are encrypted at rest with `BETTER_AUTH_SECRETS`, the same versioned secrets better-auth signs with. The list form (`2:new,1:old`) seals with the first and opens with any, so a secret can be rotated without re-encrypting every row first.

### Outbound webhooks

- An event and its delivery jobs commit in the same transaction, through the outbox.
- No event is stored when no enabled Endpoint subscribes to it; a disabled Endpoint accumulates nothing, but disabling it doesn't cancel deliveries already accepted.
- Delivery is at least once, in no particular order. Receivers deduplicate on the `webhook-id` header.
- A delivery being attempted is claimed with a lease, so a crashed worker can't strand it.
- An Endpoint's URL is its Project's to choose, so it is requested only through `@repo/public-url`, the guard hosted attachments use: https, every address its host resolves to public, the request pinned to a checked address, no redirect followed. Saving an Endpoint refuses what needs no lookup (the scheme, a literal private address); delivery checks the rest each time, since DNS can change. A host with no public address is retried like any failing Endpoint until the attempts run out; a stored URL that isn't https, or whose hostname is too long to be one, is dead-lettered at once. There is no setting that lifts this, for a Project or a deployment: a test replaces DNS and `fetch` through the Effect context.
- A signing secret is shown only when created or rotated; the previous one keeps verifying for a bounded window after rotation.
- Only a dead-lettered delivery can be replayed, and only while its Endpoint is enabled; attempt counts carry across replays.

### Templates render sealed artifacts

A Template is the send catalog; code-backed engines such as React Email are not Templates but Workspace Entries a Template's email variant links by id. A primitive variant (subject, HTML, text, flat variables with fallbacks) is live as soon as it is saved. Handlebars-style logic at save time was rejected because real templates need arrays and conditionals.

An Email Workspace's source is Git stored in object storage: content-addressed objects in S3, branch refs in Postgres, a lock per workspace (a write that finds it held is refused as busy; a first read, which only needs the scaffold finished, waits for it), throwaway worktrees for each build, so no volume is needed. Authors edit `dev`; Publish installs dependencies (public npm only) and builds in the template builder, seals each Entry into an artifact in object storage, and advances `main` only if every step succeeded. The builder is the only thing that mutates workspace Git. A send renders the sealed artifact in a constrained isolate; it never runs workspace source. The artifact leaves `react` external and the renderer links the isolate runner's copy beside it before each render, because hooks fail across two Reacts; so `react` must stay installed next to the isolate runner in each image, which the runner also imports itself. When a workspace's own source fails to install, bundle or render, the builder's error carries what the tool said in `detail`, and the api answers a failure that has one as a 422 whose `detail` the dashboard shows to the Project's members. So `detail` is written only from the workspace's tools, with the checkout's and the render's temp directories cut from its paths, and a failure of the host itself (no temp directory, an isolate that could not be started) gets none and stays a 500. Workspace kinds are a static registry in `packages/templating/src/kinds/`, so a future engine reuses the same build, seal and render path.

### Cloud and self-hosted run the same code

Plans and Usage limits come from Stripe through better-auth's Stripe plugin. Without the Stripe keys, every limit is unlimited and billing disappears: that is the self-hosted edition, not a separate build.

### Development runs with nothing real behind it

`EMAIL_BACKEND=fake` replaces SES with a stand-in (`packages/provider-aws/src/email/fake.ts`): it accepts sends, verifies identities and Domain records at once without AWS or public DNS, and reports outcomes for SES's mailbox simulator addresses through the same ingest SES notifications reach, so suppression and Webhook Events behave as they would. It needs none of the `SES_*` variables. `OBJECT_STORAGE=local` keeps objects under the checkout's `temp/`, and `REDIS_KEY_PREFIX` puts every Redis key under a prefix, better-auth's sessions included, so checkouts sharing one Redis never take each other's jobs.

The fake and local storage run only when `NODE_ENV` is `development` or `test`, whether asked for or left to default. The api, worker and builder images set no `NODE_ENV`, so an unset one has to mean SES and S3, and an explicit `EMAIL_BACKEND=fake` in a deployment must refuse to start: the fake marks every Delivery sent while delivering nothing, and its DNS answers would let a Domain claim pass without proof.

### React's `use-sync-external-store` shim in SSR

Nitro's bundled server can keep a runtime `require("react")` inside CommonJS it inlines from `use-sync-external-store/shim` (via `@base-ui/utils`), which loads a second React or none. `apps/site` resolves the shim to ESM that imports the bundled React (`vite/resolve-use-sync-external-store-from-react.ts`), and its image sets `NODE_ENV=production`. Delete the plugin once our Nitro version ships `experimental.cjsRequireRewrite`.
