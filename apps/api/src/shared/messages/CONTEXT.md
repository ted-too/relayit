# Messages

The act of sending: intent, lifecycle, and usage. Channel-specific delivery health lives in the channel (e.g. Email.Deliverability), not here.

## Language

**Message**:
One logical send from a Project to one or more recipients, which may go out on multiple channels. Owns cross-channel intent: Purpose, App / App Environment attribution (**via request headers** on transactional Accept — not body fields or Tags), **Tags**, schedule (`scheduled_at`), Idempotency Key, and optional `template_id` provenance. Channel-specific content and artifacts live on each **Delivery** (Channel Format, Attachments, Delivery status, Delivery Events) — not on the Message. Content is supplied **inline or** **rendered from a Template at Message create** into those Deliveries (**exactly one** content source per Accept; providing both is rejected); later Template edits do not change already-created Deliveries. Email (and other identity-bearing channels) **require an explicit From / sending identity** on the request — there is no implicit default to Sandbox Domain or a Project default Domain. Transactional entrypoints create a Message directly (Purpose=transactional): the multi-channel Message API (channels in the request), or `/messages/email` — the Resend-compatible transactional email API (Resend-shaped body, optional Relayit extensions); that facade’s response `{ id }` is the **Message id**. Marketing Messages are created only via Campaign Send — per-channel From comes from the **Campaign** (or allowlisted Campaign Send override), not an implicit default.
_Avoid_: Email, notification (as the product noun for the send); stuffing channel-only fields (e.g. email Attachments) onto the Message

**Delivery**:
The per-channel attempt of a Message (e.g. the email leg and the SMS leg of the same Message). Owns everything channel-specific for that leg: **Channel Format** (e.g. email From/to/subject/html/text/headers), **Attachments** (when the channel supports them), **Delivery status**, and **Delivery Events**. Source of truth for channel pipeline position. One Delivery per logical channel send for a Message (not one row per soft-bounce retry). After successful Provider handoff, **soft-bounce / deferral retries are owned by the Provider** — Relayit records Delivery Events and does **not** create new Deliveries or re-send for recipient 4xx. Soft bounce does not create Suppression. Relayit queue retries apply to **handoff / API** failures before or during Provider accept (e.g. circuit), not to post-accept soft bounces.
_Avoid_: Attempt, dispatch, channel send; do not confuse with **Deliverability** (Email module for health/reputation); Relayit-owned soft-bounce re-sends as new Deliveries

**Purpose**:
Whether a Message is **marketing** or **transactional**. Always set at the data level. Callers never pass it as an optional flag — it is implied by which API they use (transactional Message APIs vs Campaign / Campaign Send APIs). `/messages/email` does not accept a Topic; Topic consent is marketing-path only. Contacts apply suppression and unsubscribe only when Purpose is marketing.
_Avoid_: Category, type, kind (as the product noun)

**Tag** (Message Tag):
A caller-supplied **key/value** pair for search, filtering, and webhook payloads about a send. Owned by the **Message** (and/or **Campaign Send**) at create time — not a Project-global name catalog — and **immutable** afterward. Campaign Send Tags are applied to fan-out Messages unless a Message overrides a key. Distinct from **App** / **App Environment** (first-class attribution fields, not Tags) and from **Contact Tag** (separate map on Contact — same key string is unrelated). No reserved Message Tag key list; platform fields travel as nested webhook payload fields, not as Tags.
_Avoid_: Metadata, label, attribute (as the product noun); using Tags for App or App Environment; conflating with Contact Tag; treating Tags as reusable name-only labels shared across Messages

**Webhook Endpoint**:
A Project-scoped URL and signing secret that Relayit POSTs **Webhook Events** to (HMAC-signed payloads). Many Endpoints per Project are allowed. Each Endpoint has an **allowlist of event types** (opt-in; empty means none) and may also filter by **Message Tags**. May be **enabled** or **disabled**: while disabled, Relayit does not POST (new emissions and in-flight retries pause); a **match** still counts for recording so the event can be replayed after re-enable. Signing secret supports **rotation with a dual-secret window**: current and previous secret coexist so receivers can verify either until previous is cleared or the window ends; Relayit signs with the current secret. Failed HTTP deliveries are retried with backoff; after exhaustion they enter a dead-letter state and can be manually replayed. Delivery is at-least-once with no ordering guarantee; each Webhook Event includes a stable idempotency id for receiver dedupe.
_Avoid_: Callback, hook, notification URL (as the product noun)

**Webhook Event**:
An outbound notification to a Webhook Endpoint. **Only persisted when at least one Endpoint matches** (event type on allowlist and Message Tag filter, if any) — enabled or disabled; if none match, emission is a no-op (nothing recorded, no HTTP). Type names are **channel-agnostic** (not Resend’s `email.*` prefixes) — e.g. `delivery.bounced`, `delivery.skipped`, `message.sent`, `message.scheduled`, `message.failed`, `campaign_send.completed`, `domain.created`, `contact.updated`. Covers the same *categories* Resend supports (delivery outcomes, domain lifecycle, contact lifecycle) plus Message / Campaign Send status changes — not a drop-in for Resend webhook type strings. Emitted **per Message / Delivery** (Campaign Sends can produce large volumes); soft-bounce / deferral updates are Delivery Events on the same Delivery (not a new Delivery per retry). On transactional Accept, **`message.scheduled`** fires only when `scheduled_at` is set; an immediate Accept does not emit a `message.*` event by itself (HTTP `{ id }` acknowledges Accept). **`message.sent`** fires when Deliveries have reached Provider accept for a successful send rollup (single-channel email: when that Delivery → `sent` / Usage sticks) — not on HTTP Accept (unlike Resend’s `email.sent`, which is API-success-timed). **`message.failed`** covers terminal failure rollups. A Delivery that never reaches the Provider (consent, Suppression, etc.) emits `delivery.skipped` with a **reason** in the payload (e.g. `suppression`, `unsubscribe`) — not a separate `message.suppressed` type. `contact.*` events fire for single-Contact API/UI writes and for Contact upserts on transactional Message Accept; **not** for bulk/CSV Contact import rows. Inbound receive is **out of scope** until inbound is a product surface. Payloads may include Message Tags. HTTP delivery is **at-least-once**: each Webhook Event carries a stable **idempotency id** so receivers can dedupe retries and dead-letter replays of the same event (same id across HTTP attempts; a new logical emission gets a new id). **No ordering guarantee** — not globally, not per Endpoint, not per Message/Delivery; receivers must not rely on arrival order.
_Avoid_: Delivery Event (internal — may trigger a Webhook Event), Webhook Delivery (HTTP attempt implementation); `message.suppressed` (use `delivery.skipped` + reason); persisting events when no Endpoint matches

**Attachment**:
A file associated with a **Delivery** that supports it (today: email Delivery) — metadata + content reference. Not Message-level: other channels’ Deliveries neither inherit nor ignore Message Attachments. On a Campaign Send, fan-out may attach the same underlying content to each email Delivery (content may be shared; ownership remains per Delivery). Limits (size/count) may be Plan-governed later — not separate glossary nouns yet.
_Avoid_: File, media, upload (as the product noun); Message-owned Attachments; treating Attachments as cross-channel

**Email Workspace**:
A kinded React Email authoring unit for a Project (`reactEmail` workspace kind) — a multi-file **TypeScript** source tree (shared components, dependencies, lockfile) whose **source of truth is a Relayit-hosted Git repository**: **immutable Git objects in object storage**, **branch refs (`dev` / `main` tips) in Postgres**, per-workspace lock for writers, ephemeral worktrees only for deps sync / build; refs advance only after objects are durable. A Project may have **many** Email Workspaces of this kind, each with a **Workspace Source**. Other templating engines plug in as additional workspace kinds via the same registry pattern. **Scaffolded on first use** with a valid starter commit so authors are not asked to create `package.json` / a lockfile by hand. Authors’ job is Entries (and optional shared components); they may **install public npm packages** (including exact versions) and may edit `package.json`, but **non-registry dependency specs are rejected** (no git/http/`file:`/etc.). The **lockfile is platform-regenerated** (committed by the platform) — authors do not maintain it. A `package.json` change or install action queues a **deps sync** (hardened install → commit updated lockfile only; does not publish sealed artifacts). No package allowlist. The web IDE edits via Git (commits), not an opaque whole-tree upload and not a parallel object-storage draft store. Contains **Workspace Entries** (convention: `reactEmail/<name>.tsx` with default export + typed props) that are pickable assets — not Templates themselves. **Hosted** workspaces use **`dev`** for draft commits and **`main`** only for trees that have successfully sealed: **Publish** runs a workspace build from current `dev` and **advances `main` + live sealed artifacts only if that build succeeds** (failed publish leaves `main` and live artifacts unchanged). **Preview** may ephemeral-seal/render current `dev` in the same render sandbox for the IDE — it must not advance `main` or replace live artifacts. **GitHub** workspaces **build on push** to the branch chosen at link time. Send-time rendering uses sealed artifacts only — never a live Git checkout. A failed build or deps sync does not replace a previous good live artifact for an entry. Artifact content references live outside the DB row (same spirit as Attachment content references). **TypeScript is required** (plain JS rejected). Entry ids are minted when a kind entry file is created.
_Avoid_: Template (Templates link to Workspace Entries; the workspace is not the send catalog); whole-workspace opaque replace as the only edit API; treating every file save as a live artifact publish; treating deps sync or preview as a publish; merging to `main` before a successful build; package allowlists as the product dependency model; object-storage *draft file tree* as a second source of truth alongside Git; Railway volume bare repos as the v1 Git store; mutable branch tips only in S3 or Redis; treating the customer GitHub remote as the send-time content store; repo, package (as the product noun for the workspace itself)

**Workspace Source**:
How an Email Workspace’s Git tree is authored/updated. **`hosted`** (v1): edited in Relayit’s web IDE against the object-storage-backed Git repo (at most one hosted workspace per Project per kind); draft on `dev`, publish gate to `main`. The web IDE talks only to the API; the API proxies Git/build operations to the templating builder (sole Git mutator) over the private network. **`github`** (planned seam, not v1): linked to a customer GitHub repository (0..N per Project); at link time the user picks the track branch (**defaults to the repo default branch**); on push to that branch Relayit fetches and runs the **same** build → sealed-artifact pipeline; send still never reads GitHub. v1 implements only `hosted` but keeps Entry/artifact/build contracts source-agnostic so `github` can land later without a second catalog.
_Avoid_: Treating GitHub as a second Template catalog; dual write to object-storage drafts and Git; requiring GitHub for the hosted IDE path; building every branch push by default; shipping GitHub linking before the hosted Publish loop works; browser/dashboard calling the builder directly

**Workspace Entry**:
A renderable unit inside a kinded workspace (e.g. a `reactEmail/…` React Email component). **Created when the entry file is created** under that kind’s entry convention — a **stable id** is minted then (path/filename may change later without breaking the id). Has inferred props and a sealed render artifact once a **workspace build** succeeds; until then the entry exists in the tree but is not pickable for Template links. Linked Templates render from the entry’s **last live** artifact (hosted `dev` / unpublished edits are invisible to send until a successful **Publish**; GitHub until a successful build-on-push). A Template’s `reactEmail` email variant stores that **workspace entry id** as its link. Many Templates may link the same entry; deleting or breaking an entry does not delete Templates — linked variants are marked **broken** (visible on the Template) and **new sends that need that channel are rejected** until relinked or switched to another engine/content. React Email entries **export `subject(props)`** (or a string `subject`) so Accept can render Channel Format subject without stuffing subject onto the Template variant; request `subject` still overrides when provided.
_Avoid_: Template; treating the filename stem as the Template id or as the durable link target; silently clearing the link on entry delete; requiring a separate register step before the file exists

**Template**:
Reusable send content scoped to a Project. Addressed on the send path by **id** (`tmpl_…`) **or** **slug** (unique among active Templates in the Project). Has a required **name** for humans/UI — **not unique**; on create (and when name changes) Relayit **auto-generates `slug` from `name`** (stable API handle). Purpose-agnostic — the same Template may be used for transactional Messages and for Campaigns. May be created with **name only**; channel variants are attached afterward. Holds **per-channel variants** (email, later SMS, …): each variant picks an **engine** and attaches content. Multi-channel send selects **one** Template **id**; each requested channel uses that Template’s variant. If any requested channel lacks a variant, or a linked variant is **broken**, the **whole Message is rejected** (no partial accept). Email engines today: **primitive** (email **`content`** jsonb `{ subject, html?, text? }` + **`variables`** map name→`{ type: string|number; fallback? }` — Resend-shaped, no if/else, no objects/arrays; no code execution; **no Email Workspace / Git / builder**; variant edits are **live on save**) and **reactEmail** (link by **Workspace Entry id** only — `content` and `variables` are null; Message create runs that entry’s sealed artifact with structured props — including objects/arrays; draft/Publish lives on the workspace). **One email engine at a time** per Template — not both. Switching engines is explicit (clear or replace the variant). Future workspace-backed engines follow the same pick/link pattern; channel-specific string bodies live in `content`, not parallel subject/html/text columns. Historical Messages keep `template_id`. At Message create, Relayit **renders** each used variant into Channel Format on each Delivery and records `template_id` on the Message; later Template or workspace edits do not change already-created Deliveries. When a Template is the content source, overrides are limited to an allowlist (e.g. `from`, `subject`, `reply_to`) — not the HTML/text body; those overrides are not a second content source. **Archive** Template: cannot be used for new Messages or Campaign Sends (a Campaign Send that still points at an archived Template fails until updated); historical Deliveries keep rendered Channel Format and Messages keep `template_id`.
_Avoid_: Layout, theme; treating name as the send-path handle (use slug or id); caller-supplied slug at create (platform derives it from name); treating a channel engine as the Template itself; treating the sealed artifact as the editable definition; auto-creating Templates from workspace filenames; requiring a channel variant at Template create; partial multi-channel accept when a variant is missing; dual email engines on one Template; putting primitive content in an Email Workspace; draft/Publish gates on primitive variants; stuffing reactEmail subject/html/text/variables onto the variant alongside a Workspace Entry link

**Template Variable**:
A named input for rendering a **primitive** Template variant. Stored as a map keyed by variable name: `{ type: "string" | "number"; fallback?: string | number }` (fallback optional; when present it matches `type`). No separate `required` flag — if a variable has **no fallback**, Accept/Campaign Send **must** supply a value or the request fails for that Message (Resend-compatible). Placeholders are flat in subject/html/text (no if/else, no object/array paths). Callers supply a values map at Message create or Campaign Send (may differ per recipient on a Campaign Send). Extra undeclared fields are ignored. **reactEmail** does not use Template Variables — it uses structured **props** from the linked **Workspace Entry**’s inferred TypeScript types (scalars, objects, arrays).
_Avoid_: Merge tag, placeholder, data field (as the product noun); `required: boolean` on primitive variables; objects/arrays/conditionals in the primitive engine; a separate caller-maintained JSON Schema as the product contract; JS-only React Email source; treating reactEmail props as Template Variables

**Campaign**:
A durable marketing definition scoped to a Project (e.g. “Cart Abandonment”, a newsletter), addressed by **id** in APIs. Has a required **name** for humans/UI — **not unique** (duplicates allowed); name is not an API handle. Always has a Topic (consent scope) and a Template (content, by Template id). Topic and Template may be changed later; subsequent Campaign Sends use the Campaign’s current Topic for consent and current Template for render. If the Campaign’s Topic or Template is **archived**, new Campaign Sends fail until the Campaign is reassigned to an active Topic / Template. Holds **per-channel From** sending identities (email first; SMS later) — fan-out Messages inherit the From for each requested channel unless an allowlisted Campaign Send override supplies `from` for that channel. Setting a channel From requires it to be **send-ready** then (usable Domain or Sandbox Domain); if that identity later becomes unusable, the Campaign is left as-is and Campaign Send accept / send time re-checks. Content comes only from the Template — applied when a Campaign Send fans out Messages (render at Message create), not when the Campaign is merely saved. No required channel From at Campaign create; a Campaign Send that needs a channel without a From for that channel fails. **Archive** Campaign: cannot start new Campaign Sends; already accepted / in-flight Campaign Sends and their Messages continue under existing rules (Domain pause, cancel, etc.); history retained; archived Campaigns are read-only. Not a single blast — executions are Campaign Sends. All Messages from this path have Purpose=marketing.
_Avoid_: Broadcast (Resend’s term — not ours), blast, newsletter (a use case, not the noun); inline content on the Campaign; a single Campaign-wide From; treating name as a unique API key; slug (as a Campaign handle)

**Campaign Send**:
One execution of a Campaign. Targets a Segment and/or an explicit Contact list (including a single Contact). May record optional App / App Environment so Contacts resolve at that furthest scope while the Campaign definition stays Project-scoped. May be scheduled for later (`scheduled_at`). Fans out into Messages **at accept** (when the Campaign Send is created) — each Message is rendered into Channel Format on its Deliveries from the Campaign’s Template with `template_id` on the Message; allowlisted overrides (e.g. `from`, `subject`, `reply_to`) may apply at Send/Message create. Each requested channel’s From is inherited from the Campaign’s per-channel From unless overridden; From must resolve to a usable Domain or Sandbox Domain at accept (and again at send time if Domain state changed). Attachments on the Send are applied to each fan-out Message’s email Delivery (shared content reference allowed). Messages then queue like normal until `scheduled_at` if set. Later Template edits do not affect those Deliveries. Has a coarse lifecycle status only (`running` | `completed` | `failed` | `canceled`); per-recipient/channel detail lives on Messages and Deliveries.
_Avoid_: Run, blast, broadcast; do not conflate with Delivery (per-channel attempt of a Message)

**Delivery status**:
Pipeline position for a Delivery: `queued` → `sending` → `sent` | `failed` | `skipped` | `canceled`. `skipped` means never handed to the Provider for policy reasons (consent, Suppression, etc.); the corresponding Webhook Event is `delivery.skipped` with a reason. `canceled` means explicitly canceled before Provider accept (from `queued`, or `sending` if not yet accepted) — e.g. scheduled send withdrawn. After `sent`, cancel is not allowed; later outcomes are **Delivery Events** only.
_Avoid_: delivered, bounced, complained (as Delivery status values — those are event kinds); suppressed (as Delivery status — use `skipped`)

**Message status**:
Coarse rollup over a Message’s Deliveries for list UIs: `queued` | `sending` | `sent` | `failed` | `partial` | `skipped` | `canceled`. `partial` means mixed Delivery outcomes (e.g. email sent, SMS failed). Derived from Deliveries — not the source of truth for a single channel.
_Avoid_: Treating Message status as the source of truth for a single channel

**Delivery Event**:
A recorded provider or channel outcome after (or about) a Delivery. First-class kinds: `accepted`, `delivered`, `delivery_delayed`, `bounced`, `complained`, `opened`, `clicked`. Does not replace Delivery status. Distinguish hard vs soft bounce in event detail: hard bounce creates/updates **Suppression** at severity `all`; soft bounce / `delivery_delayed` is Provider-owned retry territory — record the event, do not suppress, do not create a new Relayit Delivery; the Delivery becomes `failed` only when the Provider reports permanent failure or that it has given up. A complaint creates or updates Suppression at severity `marketing`. May trigger a **Webhook Event** (e.g. `delivery.bounced`). Policy skips before Provider handoff are Delivery status `skipped` / Webhook Event `delivery.skipped`, not Delivery Events.
_Avoid_: Event alone (too generic), Engagement (usually means opens/clicks only); treating soft bounce as a Relayit re-send trigger; `deferred` / `rejected` as kind names (use `delivery_delayed` / bounce detail)

**Idempotency Key**:
A caller-supplied key scoped to a Project that makes a create-send request safe to retry. Applies to transactional Message APIs and to Campaign Send. On `/messages/email`, supplied only via the **`Idempotency-Key` header** (not a body field). Replaying the same key returns the original Message or Campaign Send; a different body with the same key is ignored (original is returned, not rejected). Keys expire after **24 hours**.
_Avoid_: Request id, dedupe token (as the product noun)

**Usage**:
Counted send activity against the Project’s **Billing User** Plan entitlements for the current **Billing Period**. Metered per **Delivery** against a single ledger counter per bucket (not a separate reserved-vs-confirmed state): Accept **reserves** by consuming headroom; that reserve **sticks** as consumed when the Provider accepts the message (Delivery → `sent`) — “confirm” means the reserve is not released, not a second phase. Provider-side soft-bounce retries do not create additional Relayit handoffs or Usage. Bucketed by **Purpose × Channel × Provider kind** (managed vs customer-connected/BYO). BYO Deliveries are still metered on the Plan but priced/limited substantially cheaper than managed. All Projects that share the same Billing User draw from that User’s buckets. At Message / Campaign Send **accept**, Relayit reserves for the Deliveries that would be created (for email, against the Domain’s **active Provider** kind); if a reserve would exceed a bucket, the whole request is rejected (no partial Campaign Send / Message). If Accept fails before a durable success is returned to the caller, the reserve is **released** and no Message is committed. After a successful Accept, a reserve is **released** if that Delivery never hands off (`skipped`, `canceled`, or failed before Provider accept); later soft-bounce / deferral does not un-confirm or re-meter. If handoff **fails over** to a Provider of a different kind, the original reserve is released and Usage is reserved against the kind that actually handed off (that reserve sticks on success; handoff may fail if that bucket is exhausted). Skips and cancels before send therefore do not consume Usage.
_Avoid_: Quota alone (quota is the limit; usage is what was consumed), billing, invoice, overage (not modeled until Billing context exists); a separate reserved-vs-confirmed Usage ledger
