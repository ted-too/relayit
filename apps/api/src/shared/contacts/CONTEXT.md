# Contacts

Recipients of messages within a tenant scope. Suppression and unsubscribe apply to the contact only when the Message **Purpose** is marketing, not transactional.

## Language

**Contact**:
A durable recipient identity within the furthest tenant scope in use. Scope is Project when App and App Environment are unset; otherwise App Environment. Messages resolve to contacts; the same person may be reached on multiple channels over time. A Contact may belong to zero or more Segments and is never owned by a Segment. May carry **Contact Tags**. **Uniqueness**: one Contact per **primary channel address** within that furthest scope (email-first: same email ⇒ same Contact; writes upsert). Email addresses are compared and stored normalized (trim + lowercase). Further addresses may attach to an existing Contact later. Changing the primary address to one already used by another Contact in scope is **rejected** (no auto-merge). **Delete** is a **soft delete**: the Contact is removed from targeting (Segments, future Campaign Sends) but the row is retained so **Suppression** and **Unsubscribe** on that address survive; a later upsert of the same primary address in scope revives the Contact without clearing those stops (cannot launder a bounce/complaint by deleting). Historical Messages keep their recipient snapshot. Single-Contact creates/updates via API or UI may emit `contact.*` **Webhook Events**. Transactional Message Accept upserts (e.g. `/messages/email` recipients) also emit `contact.*` for **creates and updates** (including revive). **Bulk/CSV import does not** emit per-row `contact.*` events.
_Avoid_: Recipient (as the durable noun — recipient is a role on a send), user (that's Tenancy), address alone

**Segment**:
An internal targeting set over Contacts for Campaign Sends only (static membership and/or filters), scoped to a Project. Addressed by **id** in APIs; has a required **name** for humans/UI — **not unique**. Not used by transactional Message APIs — those take explicit recipients. Used by the sender to decide who to target — not by the recipient to manage preferences. Membership makes a Contact a candidate only; Topic Unsubscribe and Suppression can still skip them. When a Campaign Send carries App / App Environment, membership is interpreted against Contacts in that furthest scope. **Archive** Segment: cannot be targeted by new Campaign Sends; a Campaign Send already accepted that targeted it keeps its fan-out Messages (membership was resolved at accept).
_Avoid_: Audience (easy to overload with consent), list (as the product noun), Topic (that's consent); treating name as a unique API key

**Topic**:
A recipient-facing marketing preference category scoped to a Project (e.g. newsletter, product updates). Addressed by **id** in APIs; has a required **name** for humans/UI — **not unique** (preference page may show duplicate names; id is canonical). Contacts opt in or out per Topic, or unsubscribe from all marketing. The preference page shows Topics (and global opt-out), not Campaign names. If a Contact has no preference recorded for a Topic, treat as opted-in (unless globally unsubscribed from all marketing). Distinct from Segment — Segments are for targeting; Topics are for consent. **Archive** (soft delete): cannot be chosen for new Campaigns; existing Campaigns keep the reference until the Project reassigns Topic; preference page hides archived Topics for new opt-in; retained Unsubscribes for that Topic still apply.
_Avoid_: Segment, Audience, Subscription (collides with billing Plan), Preference (as the countable product noun); treating name as a unique API key

**Suppression**:
A deliverability/compliance stop on a specific channel address of a Contact (e.g. one email or one phone), with severity **`marketing`** or **`all`**. Scoped with the Contact (furthest App Environment). Stored on the Contact record (not a separate ledger); survival across Contact **soft delete** is what retains it for that address until revive/upsert. Hard-bounce Delivery Events create/update Suppression at severity `all` (blocks every Purpose on that address). Complaint Delivery Events create/update Suppression at severity `marketing` (blocks Campaign Sends to that address only; transactional still allowed). A Project may also **manually add or remove** Suppression on an address (same severities). Other addresses on the same Contact are unaffected. Blocks regardless of Topic opt-in when applicable. On transactional Message Accept (e.g. `/messages/email`), severity `all` addresses are **stripped** from the Delivery’s recipients; if none remain, Accept is **rejected**. Severity `marketing` does not affect transactional Accept. When stripping occurs but Accept still succeeds, the Accept response keeps the Resend-shaped Message `{ id }` and may include a **Relayit-only** field listing stripped addresses and reason (not required for a basic Resend-shaped client). At handoff, severity `all` is **re-checked** the same way (strip again); if none remain, the Delivery **fails** before Provider accept and the Usage reserve is released (not `skipped`).
_Avoid_: Ban, blocklist (as the product noun), Unsubscribe (consent — distinct from Suppression)

**Unsubscribe**:
The contact's opt-out from a Topic, or from all marketing Topics (global marketing opt-out). Global opt-out is a flag on the Contact; per-Topic opt-outs are separate preference rows tied to that Contact. Global opt-out blocks every Campaign Send; it does not block transactional Messages (e.g. `/messages/email`). Topic Unsubscribe is channel-agnostic — it blocks every Delivery on that marketing Message (email, SMS, etc.), not one channel only. Not expressed by leaving a Segment. Survives Contact soft delete with the Contact row; a revived/upserted Contact keeps those preferences.
_Avoid_: Opt-out (as the sole product noun), suppression (related but distinct — unsubscribe is consent; suppression is deliverability/compliance stop)

**Contact Tag**:
A caller-supplied key/value pair on a **Contact** for search, filtering, and webhook payloads about that Contact. Separate map from **Message Tags** — same key string on a Contact and on a Message are unrelated. Not used for App / App Environment (those are first-class fields). No reserved key list shared with Message Tags.
_Avoid_: Tag alone when Message Tag is meant; Metadata, label (as the product noun); stuffing App / App Environment into Contact Tags
