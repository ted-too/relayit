# Email

The email channel: how a project sends and receives email-related delivery through Relayit.

## Language

**Domain**:
A **Project-scoped** DNS-backed sending domain (Resend Team–like — not User-owned across Projects). The Project adds and verifies it per Provider (e.g. `mail.acme.com` on managed SES vs on a customer-connected SES). Setup is **Resend-style direct DNS** per Domain↔Provider pairing (customer publishes the records Relayit shows for that Provider) — not a customer-facing DNS proxy/CNAME indirection layer, and **no separate ownership TXT** on the normal verify path (controlling the pairing’s DKIM + MAIL FROM DNS is enough to become send-ready). Assisted publish at the DNS host (e.g. Domain Connect applying those same records) is still that publish step — not a separate Domain lifecycle or setup model. Assist may be offered per DNS-record group the Project is shown (e.g. ownership challenge, pairing auth, DMARC), so the customer can choose which groups to publish. **Send-ready** for a pairing requires that pairing’s **DKIM** and **MAIL FROM** (MX + SPF) verified; **DMARC** is Domain-scoped and **recommended** (default `p=none`), not required to send. Adding another Provider is **additive**: that pairing gets its own record set with **unique hostnames** (DKIM selector, MAIL FROM / return-path hosts, etc.) so pairings do not overwrite each other; failover-eligible pairings must **keep** their records published. Turning **failover eligibility off** does not remove the pairing or drop its DNS from Relayit’s required set (it simply won’t receive failover traffic). **Removing** a pairing drops that pairing’s unique hosts from the required set (customer may delete them); the **active** pairing cannot be removed until the Project switches active or removes the Domain. **DMARC** remains when a pairing is removed. **SPF** for sending authorization lives on each pairing’s **MAIL FROM / return-path** host, Resend-style — not a merged SPF TXT on the From domain as the platform model (a Provider adapter may still require extra vendor-specific records). Distinct from **Sandbox Domain**. **One Domain per FQDN** as the live send owner — the same FQDN cannot be an active sending Domain for two Projects (a pending claim may exist alongside the source). Moving a FQDN between Projects is a rare **claim/transfer**: the destination Project **adds** the FQDN on the same create path and **chooses** the Provider backend for the new primary pairing (same picker as normal Domain create). If another Project holds it, create **enters claim** (Domain exists in a claiming state with an **ownership TXT** to publish) — ownership challenge applies **only for claim**, not normal setup. Claim is **self-serve** on that challenge (no recent-activity support gate). While claim is pending, the **source keeps send** (live owner); the destination cannot send on that FQDN and may abandon by removing the claiming Domain. **At most one pending claim** per FQDN — a second destination’s create-into-claim is rejected until the outstanding claim completes or is abandoned. A pending claim counts toward the destination’s Plan Domain cap; on success the destination keeps the slot and the source frees one. On success the Domain moves to the destination and the source immediately cannot use it (in-flight source Deliveries fail at send time, same spirit as remove). If the destination chose the **same managed backend** as the source’s pairing for that Domain, keep that pairing’s bindings/DNS and re-check send-ready; if they chose a **different** Provider (other managed backend or BYO), **tear down** the old pairing and the destination sets up fresh DNS for the new pairing. **BYO** and other failover pairings from the source are **dropped** (destination re-adds them explicitly against its own Providers). Active Provider and failover priority **reset** on the destination (the chosen pairing becomes active when send-ready). A Domain may be verified on more than one Provider. Exactly one **active Provider** is the primary send path; the first successful Provider verification becomes active; the Project may **explicitly switch** active later. Additional Provider pairings are added explicitly (each with its own record set to publish). When an additional pairing is added, it is **failover-eligible by default**; the Project may turn failover eligibility off for that pairing. At send time: try the **active Provider** first; leave active for the next pairing only on **circuit-open** or a **terminal / non-retryable** provider error — transient errors stay on active via queue backoff. Then try other **verified + failover-eligible** pairings in a **Project-defined priority order** (newly added pairings append after active by default; not weighted load-spreading in normal operation). Same-vendor platform HA under a single pairing (e.g. managed SES internals) may exist invisibly and is not a separate product noun. Queued or scheduled Deliveries use this send-time routing (an active switch applies to already-queued work, not only new accepts). **Sandbox Domain** always sends via the managed Provider (no active-Provider switch / multi-Provider failover). May be **paused** (with a reason): while paused, **new** send requests that would use that Domain as From are **rejected up front** (no Message / Campaign Send accepted for that identity). Messages / Deliveries already queued or scheduled that would use it **fail at send time** with a Domain-paused cause (not `skipped`, not auto-cancel, not held until unpause). **Remove** detaches the Domain from the Project: it cannot be used for new sends; the FQDN becomes available for another Project after removal; queued/scheduled Deliveries that would use it fail at send time (same spirit as pause); historical Messages keep their recorded From. Verification and DNS config remain while the Domain exists (including while paused). Pause is distinct from Provider circuit breaking (vendor health) and from Webhook Endpoint disable.
_Avoid_: Sending identity (as the UI noun), hostname alone, website; Sandbox Domain; Custom Domain; customer-facing DNS proxy as the setup model; per-Project ownership TXT on the normal verify path; User-owned Domains shared across Projects; silently migrating BYO Provider credentials across Projects on claim; silently keeping source DNS when the destination picked a different Provider on claim; silent multi-Provider routing without an explicit Domain↔Provider pairing; weighted multi-Provider spreading as normal send behavior

**Sandbox Domain**:
A Project-scoped email **Sending Identity** usable before (or without) a verified customer **Domain** — for test/onboarding sends. **At most one per Project**, **provisioned when the Project is created**, allocated by Relayit under a Relayit-owned DNS root (the Project does not manage DNS for it). Remains available for restricted/test sends even after the Project has verified Domains. Always sends via managed Provider identities on the Sandbox Domain (no active-Provider switch / multi-Provider failover). Not a customer-DNS Domain (no DKIM/MAIL FROM publish step). Sends via a Sandbox Domain may only target **Project members** (recipient addresses must match a member User’s email in that Project). Enforced at Accept: **any** non-member recipient **rejects** the whole Accept (no strip-and-continue). Re-checked at handoff: any non-member → Delivery **fails** before Provider accept (Usage reserve released; not `skipped`). Other Sandbox knobs (watermark, lower Plan limits) may stay Plan-level and are not separate glossary nouns yet. Distinct from App Environment (attribution scope, not sending identity).
_Avoid_: Domain (the verified DNS-backed entity), test domain (as the product noun), App Environment; open recipient allowlists unrelated to Project membership; stripping non-members on Sandbox Accept

**Provider**:
Same meaning as in Channels — a delivery-vendor capability a Project uses for email (e.g. SES), managed or customer-connected. **BYO Providers are Project-owned** (same tenancy as Domains; credentials do not span Projects). Adding a BYO Provider is Plan-gated via the Project’s Billing User in cloud edition; self-hosted entitlements behave as unlimited (BYO always allowed). Lost cloud entitlement freezes BYO sends (billing-limits-reached until the Domain’s send path moves off BYO); pairings are not auto-removed. When multiple managed backends exist, ops marks one as **default**; Domain create / additive pairings may choose a managed backend or BYO, and omitting a choice uses the **current** ops default (no per-Project sticky store). With only one managed backend, that choice is implicit. BYO may be added/removed freely. For email, Domain setup per Provider pairing is Resend-style direct DNS (records may differ by vendor; managed and BYO of the same vendor family should stay as similar as possible). Platform/admin managed-vendor wiring is out of the product glossary; ops cannot delete a managed backend while Domain or Sandbox pairings still reference it.
_Avoid_: Integration, channel, connection (as the product noun); Platform Provider; User-owned BYO shared across Projects; per-Project sticky managed Provider store; treating Provider attach alone as Domain verification (Domain↔Provider pairing + DNS is required to send)

**Deliverability**:
Email-channel delivery health and signals — bounces, complaints, domain reputation, provider circuit breaking — and the channel’s answer to whether sending may proceed. Provider vendors push those delivery signals into Relayit via **Provider notification ingress** — not customer inbound mailbox receive, and not a Project **Webhook Endpoint**. A **paused Domain** is a Domain-level send stop (may be set from Deliverability signals or explicitly); it is not the same as a Provider circuit open.
_Avoid_: Usage (that is Messages), Message status as the product noun for the whole send; conflating Domain pause with Provider circuit breaking; conflating Provider notification ingress with inbound receive or customer Webhook Endpoints

## Modules

- **Providers** — vendor capability attached to the Project (managed or customer-connected); setup assistance, not a full provider control-plane proxy
- **Sending Identity** — module for setup required to send *as* / *from* on this channel; for email the product entities are **Domain** (verified per Provider via BYODKIM / DNS) and **Sandbox Domain** (pre-verification / test sending identity)
- **Deliverability** — channel delivery signals and send-gating for email
